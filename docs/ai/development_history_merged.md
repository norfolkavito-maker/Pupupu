# Knowledge Base / Development History: Zapret‑Manager Windows

Документ объединяет два слоя информации:

1. Реестр инцидентов, багов, P‑кодов, TASK 1–11 и UI/UX‑жалоб.
2. Общую техническую сводку по архитектуре, модулям, стратегиям, меню, DoD и приоритетам разработки.

Назначение: использовать как входной документ для следующего агента, чтобы при сборке или рефакторинге Windows‑версии Zapret‑Manager не потерять требования, баги, ограничения безопасности и уже выявленные проблемы.

---

## 1. Реестр выявленных уязвимостей и критических ошибок

### P‑001: Path Traversal при распаковке

Проблема: использование `ZipFile.extractall()` без валидации имён файлов позволяло архиву записывать файлы вне целевой папки.

Риск: повреждение файлов проекта, перезапись пользовательских или системных файлов, небезопасная распаковка сторонних архивов.

Требуемое решение: использовать `safe_extract`, которая проверяет, что итоговый путь назначения находится строго внутри разрешённой runtime‑папки.

Критерий приёмки: ни один файл из архива не может быть распакован выше целевой директории даже при наличии `../`, абсолютных путей или Windows‑вариантов path traversal.

### P‑002: Перезапись пользовательских конфигов и списков при обновлении

Проблема: обновление `zapret-win-bundle` могло стирать пользовательские файлы, например `ipset-discord.txt` и другие кастомные списки.

Риск: потеря пользовательских настроек, потеря вручную добавленных правил, невозможность воспроизвести рабочую конфигурацию после обновления.

Требуемое решение: реализовать merge‑логику: бинарники и runtime‑артефакты обновляются, пользовательские текстовые списки и кастомные стратегии сохраняются.

Критерий приёмки: при обновлении bundle пользовательские списки не удаляются и не перезаписываются без backup.

### P‑003: Command Injection через shell=True

Проблема: пути и аргументы передавались в `subprocess.run(shell=True)`. При наличии пробелов, спецсимволов или вредоносного ввода это может привести к выполнению произвольных команд.

Риск: удалённое или локальное выполнение нежелательных команд, особенно опасно при запуске с правами администратора.

Требуемое решение: полностью отказаться от `shell=True` для запуска `winws.exe`, `netsh`, `ipconfig`, `schtasks`, PowerShell и прочих команд. Передавать аргументы списком: `["winws.exe", "--arg1", "..."]`.

Критерий приёмки: аудит кода не находит `shell=True` в местах, где есть пользовательский ввод, пути, URL, стратегии, домены, имена файлов или аргументы запуска.

### P‑004: Небезопасный uninstall / агрессивная очистка TEMP

Проблема: скрипт удаления пытался чистить `%TEMP%` слишком широко.

Риск: удаление посторонних временных файлов других программ или пользователя.

Требуемое решение: удалять только файлы и папки, созданные самим приложением, по известным маркерам, именам или manifest‑файлу установки.

Критерий приёмки: uninstall не удаляет ничего вне собственных директорий и временных файлов с подтверждённым происхождением.

### P‑005: Отсутствие проверки checksums

Проблема: программа скачивала исполняемые файлы без проверки контрольных сумм.

Риск: запуск повреждённых, подменённых или небезопасных бинарников.

Требуемое решение: проверять SHA‑256 для скачанных артефактов до запуска или распаковки. Для неизвестных источников показывать предупреждение и не запускать автоматически.

Критерий приёмки: runtime‑бинарники не запускаются, пока не пройдена проверка хеша или пока пользователь явно не подтвердил риск.

### P‑006: Silent Failure при действиях, требующих администратора

Проблема: редактирование `C:\Windows\System32\drivers\etc\hosts`, работа с Firewall, DNS, WinDivert и системными настройками могла выполняться без явной проверки прав администратора.

Риск: программа выглядит как работающая, но изменения не применяются.

Требуемое решение: проверять права до действия. Для системных операций предлагать перезапуск с UAC или явно сообщать, что действие невозможно без администратора.

Критерий приёмки: системные операции либо выполняются с правами администратора, либо возвращают понятную ошибку. Тихие отказы запрещены.

### P‑007: Повреждение config/state при аварийном завершении

Проблема: при аварийном завершении `config.yaml`, `state.json` или другие файлы состояния могли стать пустыми или частично записанными.

Риск: потеря конфигурации и невозможность запуска программы.

Требуемое решение: атомарная запись через временный файл, flush/sync и replace. Перед изменением критичных файлов делать backup.

Критерий приёмки: при принудительном прерывании записи старый файл остаётся валидным или доступен backup.

### P‑008: Бесконечный цикл меню при некорректном вводе

Проблема: ввод букв вместо цифр мог приводить к бесконечному циклу печати меню.

Риск: консоль становится непригодной, пользователь не понимает, как выйти.

Требуемое решение: централизованный обработчик ввода меню с валидацией, лимитом повторов и понятным сообщением.

Критерий приёмки: любой некорректный ввод возвращает пользователя к выбору без зависания и без бесконечной печати.

### P‑010: File in Use при обновлении winws.exe

Проблема: программа пыталась обновить `winws.exe`, пока процесс был запущен.

Риск: сбой обновления, частично заменённые файлы, повреждённый runtime.

Требуемое решение: перед обновлением проверять активные процессы, корректно останавливать `winws`, ждать завершения, только потом заменять файлы.

Критерий приёмки: обновление runtime невозможно начать, пока связанные процессы не остановлены или пользователь не подтвердил принудительную остановку.

### P‑014: Утечка секретов в логах

Проблема: токены, proxy‑подписки, приватные ссылки и пути могли попадать в `zapret_manager.log` в открытом виде.

Риск: компрометация подписок, ключей, URL и пользовательских данных.

Требуемое решение: централизованный sanitizer/masker для логов, bug report и диагностических архивов.

Критерий приёмки: в логах и bug report секреты маскируются. Пример: `token=abc...` превращается в `token=***`.

## 2. TASK 1–11: функциональные задачи и дополнения

### TASK 1: Предстартовая диагностика / Baseline

Жалоба: пользователь не понимает, работает ли программа, или проблема в сайте, провайдере, DNS, Discord, YouTube, игре или текущей стратегии.

Требование: если Zapret выключен, программа должна выполнить “чистый” тест 5 проблемных доменов и сохранить результат как baseline.

Что нужно реализовать:

- список доменов по умолчанию;
- возможность добавить свои домены;
- сохранение результата baseline;
- сравнение baseline с результатами после включения стратегии.

Критерий приёмки: пользователь видит разницу “без Zapret” и “со стратегией”.

### TASK 2–3: Testing Engine

Требование: нужен выбор между быстрым и полным тестом.

Quick‑тест:

- HTTP GET;
- короткий timeout;
- понятный OK/FAIL.

Full‑тест:

- DNS resolve;
- TCP handshake;
- HTTP GET;
- опционально ping, если доступен;
- итоговая причина сбоя.

Дополнения:

- progress bar в консоли;
- цветовая индикация;
- сохранение результатов;
- отсутствие зависания UI.

Критерий приёмки: пользователь понимает, что именно не работает: DNS, TCP, HTTP, timeout или стратегия.

### TASK 4: Управление проблемными доменами

Требование: вручную добавлять домены в `problem_domains.json`.

Логика:

- если тест домена провалился, программа предлагает добавить домен в problem domains;
- хранить `first_seen`, `last_seen`, `fail_count`, `last_error`, `last_strategy`;
- использовать список в тестах и авто‑подборе.

Критерий приёмки: проблемные домены не теряются и становятся отдельным набором для тестирования.

### TASK 5: Auto‑Tune / авто‑подбор стратегий

Критическое требование: не просто запускать `blockcheck`, а парсить его вывод и автоматически предлагать или применять лучшую стратегию.

Что нужно учесть:

- поддержка builtin стратегий;
- поддержка Flowseal;
- тестирование по доменным наборам;
- рейтинг стратегий;
- не применять автоматически опасные/экспериментальные стратегии без подтверждения.

Критерий приёмки: после теста пользователь получает ранжированный список стратегий и может применить лучшую.

### TASK 6: Repair Flow / стабилизация runtime

Проблема: программа не видит `bin/`, runtime скачан не полностью, отсутствуют `winws.exe`, `WinDivert.dll`, `WinDivert64.sys`, fake‑файлы или списки.

Требование: кнопка “Починить Runtime”.

Что делает repair:

- проверяет структуру runtime;
- проверяет обязательные файлы;
- останавливает процессы;
- делает backup пользовательских данных;
- удаляет повреждённые артефакты;
- заново скачивает bundle;
- сверяет хеши;
- восстанавливает пользовательские списки.

Критерий приёмки: после repair программа либо имеет валидный runtime, либо выводит точную причину невозможности восстановления.

### TASK 8–9: Диагностика и bug report

Требование: пользователь должен иметь возможность создать один ZIP‑архив для техподдержки.

Состав архива:

- `config.yaml`;
- `state.json`;
- `logs/*.log`;
- текущие правила Firewall;
- копия hosts;
- результаты тестов;
- версии бинарников;
- список активных процессов;
- маскированные подписки/секреты.

Критерий приёмки: bug report содержит достаточно данных для анализа, но не раскрывает секреты.

### TASK 10: Updater

Техническая деталь: updater должен копировать себя в `%TEMP%`, потому что не может заменить сам себя во время выполнения.

Требования:

- остановить процессы;
- сделать backup;
- скачать новую версию;
- проверить checksum;
- распаковать безопасно;
- заменить файлы;
- сохранить пользовательские данные;
- перезапустить приложение при необходимости.

Критерий приёмки: обновление не ломает runtime и не стирает пользовательские конфиги.

### TASK 11: Sing‑box / VPN‑прослойка

Требование: интеграция sing‑box как отдельного слоя.

Что нужно:

- импорт single link;
- импорт subscription URL;
- preview подписки без авто‑активации;
- сохранение `nodes.json`;
- выбор active node;
- health‑check узлов;
- пометка `[DOWN]`, если узел не работает;
- генерация конфига;
- start/stop/status sing‑box;
- проверка локальных портов.

Критерий приёмки: пользователь видит состояние узлов и не активирует сломанный узел случайно.

## 3. UI/UX‑жалобы и требования

### UX‑001: “Много текста, ничего не понятно”

Требование: добавить краткие пояснения в скобках к каждому пункту меню.

Пример: `Починить Runtime (перекачать недостающие файлы zapret-win-bundle)`.

### UX‑002: “Зависает при тестах”

Требование: сетевые тесты не должны блокировать UI.

Решение:

- вынести тесты в отдельные потоки/таски;
- показывать progress;
- позволять отменять тест;
- не терять старое состояние после отмены.

### UX‑003: “Где иконка?”

Требование: добавить tray icon.

Минимальные действия в трее:

- Start/Stop;
- Restart;
- выбрать стратегию;
- quick test;
- bug report;
- открыть логи;
- выйти.

### UX‑004: “Сломался Discord”

Требование: отдельный подпункт для ремонта Discord.

Что должно быть внутри:

- тест Discord domains/media/voice;
- авто‑подбор `--dpi-desync-split-pos`;
- проверка финских IP;
- hosts apply/remove;
- flushdns;
- отдельный Dv‑профиль.

## 4. Общая архитектура и инфраструктура

### 4.1. Полное меню и структура

Нужно реализовать текстовое главное меню, визуально похожее на оригинальный Zapret‑Manager. Главный приоритет — не “красота”, а сохранение полной логики StressOzz‑менеджера в Windows‑адаптации.

Обязательные свойства:

- проверка прав администратора;
- запуск через `run.bat`;
- запуск с UAC через `start_as_admin.bat`;
- все пункты меню существуют;
- недоделанные пункты помечаются как `not implemented`;
- программа не падает, если runtime отсутствует;
- программа показывает понятную ошибку, если нет прав администратора.

### 4.2. Конфигурация и хранение данных

Требования:

- расширить `config.yaml` Windows‑специфичными разделами;
- все пути хранить через config/AppContext;
- не использовать абсолютные `C:\Users\...`;
- логи писать в `DedZapretData/logs`;
- состояние хранить в `state.json`;
- стратегии хранить отдельно.

### 4.3. Запуск и остановка Zapret

Нужно реализовать:

- `start_zapret()`;
- `stop_zapret()`;
- `restart_zapret()`;
- запуск активной стратегии;
- сохранение PID или надёжное определение процесса;
- просмотр команды запуска;
- ручной запуск с параметрами;
- логирование всех действий.

### 4.4. Backup/restore

Требования:

- backup configs;
- backup hosts;
- backup user strategies;
- backup runtime metadata;
- restore из выбранной резервной копии;
- атомарная запись критичных файлов.

### 4.5. Сборка

Нужно добавить:

- PyInstaller spec для `ZapretManagerWin.exe`;
- инструкции сборки;
- возможность сборки через GitHub Actions / Windows.

## 5. Модули и классы

### 5.1. `platform.py` / `WindowsPlatform`

Назначение:

- определить Windows;
- проверить права администратора;
- перезапуск с UAC;
- безопасное выполнение системных команд;
- нормализация путей;
- получение системной информации.

### 5.2. `WinwsRunner`

Назначение:

- запуск `winws.exe`;
- остановка;
- restart;
- проверка статуса;
- сохранение PID;
- сбор last error;
- запрет запуска при отсутствующих fake/list файлах;
- запуск без `shell=True`.

### 5.3. `HostsManager`

Назначение:

- добавлять блоки hosts;
- удалять только собственные блоки по маркерам;
- делать backup;
- делать restore;
- выполнять `ipconfig /flushdns`;
- проверять права администратора.

### 5.4. `FirewallManager`

Назначение:

- создавать правила через `netsh`;
- удалять свои правила;
- показывать текущие правила;
- включать их в bug report.

### 5.5. `DohManager`

Назначение:

- читать текущие DNS;
- применять DNS‑профили;
- сбрасывать на DHCP;
- проверять поддержку системного DoH;
- выводить инструкцию, если автоматизация невозможна.

### 5.6. `TgProxyManager`

Назначение:

- проверять наличие Go/Rust proxy exe;
- запускать/останавливать proxy;
- генерировать MTProto secret;
- показывать `tg://proxy`;
- добавлять/удалять автозапуск.

## 13. Зафиксированные ошибки агентной разработки

### DEV‑001: Pyright error в `system.py`

После сохранения `app/zapret_manager/features/system.py` была обнаружена ошибка:

```text
[windsurfPyright Error] Line 79: Ожидается ":"
```

Что значит: синтаксическая ошибка, вероятно пропущено двоеточие в объявлении функции, класса, `if`, `for`, `try`, `except` или подобной конструкции.

Что сделать: открыть файл, проверить строку 79 и соседние строки, запустить линтер/тесты.

### DEV‑002: Ошибка replace_in_file / пустой SEARCH block

Попытка изменить `app/zapret_manager/utils/platform.py` завершилась ошибкой:

```text
Empty SEARCH block detected with non-empty file
```

Что значит: SEARCH/REPLACE был сформирован неправильно или не совпадал с текущим содержимым файла.

Что сделать: перед заменой читать актуальный файл и использовать точный фрагмент для SEARCH.

### DEV‑003: 502 Invalid URL в агентной среде

Несколько запросов к модельному API завершались ошибкой:

```text
502 Invalid URL
```

Это относится к инфраструктуре модели/провайдера, а не к логике программы. Но агент должен учитывать, что часть итераций могла быть прервана или недовыполнена.

## 14. Definition of Done

Проект считается нормально реализованным, если:

- меню полностью соответствует дереву требований;
- все пункты меню существуют, даже если часть пока `not implemented`;
- для каждой функции есть отдельный модуль или метод;
- никакая функция не хардкодит пользовательские пути;
- все изменения hosts делаются безопасно и с backup;
- все действия, требующие администратора, проверяют права;
- запуск `winws` работает с активной стратегией;
- можно выбрать Gv1 и запустить игру через менеджер;
- после закрытия игры `winws` останавливается;
- можно импортировать Flowseal стратегии;
- можно тестировать стратегии по домену;
- можно собрать exe через GitHub Actions / Windows;
- README содержит инструкцию для обычного пользователя;
- bug report маскирует секреты;
- обновление runtime не стирает пользовательские данные.
