# OPERATIONS AND QUALITY‑OF‑LIFE SPECIFICATION

## Обзор

Этот документ дополняет **PROGRAM_BLUEPRINT.md**, описывая подробные аспекты работы DedZapret Manager, связанные с операциями, удобством использования и вспомогательными функциями.  Если **PROGRAM_BLUEPRINT.md** — это карта продукта и архитектуры, то данный документ описывает, какие операции должна поддерживать программа и какие качества жизни должны быть встроены в пользовательский опыт.  Разделы ниже разбиты по важным функциональным блокам: тестирование, слой proxy/VPN, автозапуск и треевая интеграция, профили, диагностика, обновления и ремонт, резервное копирование, а также общие требования к удобству использования.

## 1. Тестирование и верификация стратегий

Тестовый движок — это один из ключевых модулей DedZapret Manager.  Цель тестов — не просто запустить стратегию, а помочь пользователю подобрать оптимальный набор параметров для конкретного провайдера и региона.  Программа должна поддерживать следующие режимы тестирования:

### 1.1 Базовый тест без zapret

* **Что делает**: проверяет доступность сервисов без активации `winws2`.  Служит контрольной точкой для сравнения с результатами других стратегий.
* **Как работает**: пробует резолвить домены, устанавливать TCP‑соединения на порты 80 и 443, отправляет HTTP/HTTPS запросы и измеряет задержку.  Результаты сохраняет для использования в рейтинге.

### 1.2 Быстрый тест текущей стратегии

* **Что делает**: за несколько секунд проверяет, что выбранная стратегия работает и не вызывает очевидных ошибок.
* **Как работает**: запускает текущую стратегию (если не запущена), делает ограниченное число проверок (например, 2–3 домена), фиксирует результат и возвращает управление.

### 1.3 Полный тест текущей стратегии

* **Что делает**: проводит полный набор проверок для активной стратегии.
* **Как работает**: валидирует наличие всех необходимых файлов, запускает стратегию, ждёт «прогрев» сети, затем выполняет полный набор проб (резолв DNS, TCP/UDP, HTTP/HTTPS, QUIC, измеряет задержку, отслеживает сбои).  По завершении останавливает стратегию, если она была временно активирована.

### 1.4 Тест выбранной стратегии

* **Что делает**: позволяет проверить любую стратегию из реестра без её применения.
* **Как работает**: валидирует стратегию, если нужно — временно запускает, выполняет проверки, сохраняет результат, затем возвращает систему в исходное состояние.

### 1.5 Тест всех базовых стратегий

* **Что делает**: прогоняет базовые стратегии (Flowseal, builtin, custom) и строит рейтинг.
* **Как работает**: сначала сохраняет состояние пользователя, затем выполняет baseline‑тест.  Далее итерируется по стратегиям: валидирует, запускает, проводит тесты, останавливает.  После завершения возвращает исходное состояние.  Результаты записываются в `strategy_runs.jsonl`, а список лучших — в `latest_strategy_ranking.json`.

### 1.6 Тест Flowseal и StressOzz стратегий

* **Что делает**: аналогично тесту базовых стратегий, но применимо к стратегиям, импортированным из Flowseal и StressOzz.
* **Особенности**: для Flowseal strategies должны быть подтверждены привязки к `winws2`, для StressOzz — отмечены как требующие нормализации при необходимости.

### 1.7 Тест слоёв (Dv/Yv/Gv/RKN/wssize)

* **Что делает**: проверяет отдельные слои Discord, YouTube, Games и дополнения (RKN, wssize) в контексте текущей базовой стратегии.
* **Как работает**: к базовой стратегии добавляет выбранный слой и выполняет тест, оценивая влияние добавления.

### 1.8 Тест произвольного домена и наборов доменов

* **Что делает**: позволяет пользователю задать свой домен либо выбрать заранее подготовленный набор (например, «Проблемные»).
* **Как работает**: использует тот же механизм проверки, что и другие тесты, но с иной входной выборкой.

### 1.9 Повторное тестирование проблемных доменов

* **Что делает**: позволяет быстро перепроверить домены, которые ранее показали ошибки.
* **Как работает**: получает список доменов из `problem_domains.json`, запускает текущую стратегию (если нужно) и тестирует только эти домены.

### 1.10 Доказательство эффекта (proof of effect)

* **Что делает**: демонстрирует пользователю, что конкретная стратегия действительно меняет сетевое поведение по сравнению с baseline.
* **Как работает**: собирает ключевые метрики (количество сбросов, тайм‑аутов, средние задержки) для baseline и выбранной стратегии и выводит сравнительную таблицу или график.  Может автоматически генерировать отчёт для разработчиков.

### 1.11 Хранение результатов тестов

* Все результаты тестов сохраняются в `DedZapretData/data/telemetry/strategy_runs.jsonl` в виде JSON‑строк.  Последний рейтинг сохраняется в `latest_strategy_ranking.json`.  Список проблемных доменов — в `problem_domains.json`.
* Каждая запись должна содержать метаинформацию: время запуска теста, версию программы, выбранную стратегию, набор доменов, результат проверки, наличие ошибок, предупреждений и т.д.


## 2. Слой VPN/Proxy (sing-box)

DedZapret Manager может работать совместно с sing‑box — современным многопротокольным прокси‑движком.  Proxy‑слой отделён от zapret‑runtime и может работать независимо или совместно.  Основные функции слоя:

### 2.1 Импорт и управление узлами

* **Импорт узла**: должен поддерживать схемы `vless://`, `vmess://`, `trojan://`, `ss://`, JSON‑описания sing‑box, YAML‑файлы (subset clash), base64‑подписки или plain‑subscriptions.  При импорте выполняется валидация и сохранение параметров узла.
* **Предпросмотр подписки**: скачивает подписку, парсит её, показывает пользователю список доступных узлов и их параметры.  Активный узел не меняется без явного выбора.
* **Обновление подписки**: скачивает актуальное содержимое и обновляет существующие узлы.  Если активный узел больше не присутствует, пользователю предлагается выбрать новый.
* **Удаление узлов**: пользователь может удалить ненужный узел.  Программа должна хранить историю удаления для отчётности.

### 2.2 Конфигурация и запуск

* **Сборка конфигурации**: создаёт конфигурационный файл для sing‑box на основе активного узла, локальных портов (SOCKS, HTTP, mixed), режима DNS и правил маршрутизации.  Файл должен храниться в `DedZapretData/runtime/singbox/config.json`.
* **Запуск процесса**: проверяет наличие бинарника sing‑box, валидность активного узла и собранной конфигурации, запускает процесс, записывает PID и статус.  При необходимости может включить системный proxy Windows.
* **Остановка процесса**: завершает sing‑box, освобождает порты, отключает системный proxy.
* **Здоровье**: проверяет, что порты слушают, процесс жив и работает корректно.  При ошибках выводит понятные сообщения.
* **Режимы работы**:
  * `proxy only` — активируется sing‑box без запуска zapret/winws2.
  * `winws2 only` — активируется DPI‑runtime без proxy.
  * `combined` — активируются оба режима.
  * `disabled` — ни sing‑box, ни winws2 не запущены.

### 2.3 UX для proxy слоя

* В UI должен быть выделенный раздел “VPN / Proxy”.  Здесь показываются параметры:
  * **Proxy mode** (ON/OFF/Combined).
  * **Engine** — всегда `sing‑box`.
  * **Local ports** — SOCKS и mixed.
  * **System proxy** — вкл/выкл.
  * **Active node** — имя узла.
  * **Количество узлов** и подписок.
* Пользователь может:
  * импоритировать или обновить подписку;
  * выбрать узел;
  * запустить или остановить proxy;
  * включить или отключить системный proxy;
  * посмотреть лог proxy.


## 3. Автозапуск и системный трей

DedZapret Manager должен предоставлять полноценную интеграцию с Windows‑окружением: возможность запускаться при входе, сворачиваться в трей и не занимать место на панели задач, отображать статус и давать быстрый доступ к действиям.

### 3.1 Автозапуск

* Использовать **Task Scheduler** вместо папки автозагрузки.  Задача должна иметь понятное имя, запускаться с наивысшими привилегиями, иметь корректный путь к исполняемому файлу и передавать нужные аргументы для старта в трее или восстановления последнего профиля.
* Функции:
  * `enable_autostart()` — создаёт или обновляет задачу.
  * `disable_autostart()` — удаляет задачу.
  * `repair_autostart()` — проверяет существование и корректность задачи, переустанавливает при необходимости.
  * `get_autostart_status()` — возвращает состояние (ON/OFF), путь к задаче, параметры запуска и флаг «minimized».
  * `set_start_minimized()` — переключает запуск в трее.
  * `set_restore_last_profile()` — указывает, нужно ли восстанавливать последний активный профиль при автозапуске.
* Устанавливая автозапуск, программа должна отображать, какие изменения будут внесены (создание задачи, установка прав и т.д.), и предлагать откат.

### 3.2 Трей

* Модуль трея состоит из фонового процесса, библиотеки для отображения и меню.  Он не содержит бизнес‑логики, а вызывает функции `core.commands`.
* **Статус‑индикатор** (иконка) должен отражать текущее состояние:
  * Серый — всё выключено.
  * Зелёный — включён winws2.
  * Синий — включён только proxy.
  * Фиолетовый — выполняется тест или длительная операция.
  * Жёлтый — предупреждение (например, отсутствуют обновления, проблемы со стратегией).
  * Красный — критическая ошибка (запуск не удался).
* **Tooltip** должен показывать краткую информацию: активный профиль, PID процесса, локальные порты, последний тест.
* **Контекстное меню** предоставляет основные действия:
  * Старт / Стоп текущего профиля
  * Перезапуск
  * Список профилей
  * Список стратегий
  * Тесты
  * Proxy/VPN
  * Диагностика
  * Логи
  * Создать bug report
  * Настройки
  * Выход с безопасной остановкой
* В режиме минимизации на системной панели должен оставаться только трей.  Главное окно появляется лишь по запросу пользователя.


## 4. Профили сценариев

Профиль — это не просто ссылка на одну стратегию.  Это полноценный сценарий, включающий в себя параметры winws2, выбор прокси узла, сетевые параметры и настройку автозапуска.

### 4.1 Модель профиля

Профиль описывается JSON‑или YAML‑структурой со следующими полями (пример приведён в **PROGRAM_BLUEPRINT.md**):

* `id` — внутренний идентификатор профиля.
* `name` — отображаемое имя.
* `description` — описание для пользователей.
* `winws2` — блок, описывающий:
  * включён ли runtime;
  * базовую стратегию (`base_strategy`);
  * выбранные слои (`youtube_layer`, `discord_layer`, `games_profile`, `rkn`, `wssize`);
* `proxy` — блок, описывающий:
  * включён ли proxy;
  * id активного узла;
* `network` — блок, описывающий режим DoH, список блокировок hosts, флаги блокировки QUIC и TCP timestamps;
* `autostart` — блок, описывающий, будет ли профиль запускаться при старте Windows и будет ли приложение свёрнуто в трей;
* `watch` — блок, описывающий список процессов, при запуске которых следует автоматически включать профиль (например, Discord.exe), и опции автозапуска и автоостановки.

### 4.2 Встроенные и пользовательские профили

* **Встроенные профили**: безопасный режим (Default Safe), «YouTube», «Discord», «YouTube + Discord», игровые режимы (Gv1–Gv4), «Proxy only», «Combined» и т.д.
* **Пользовательские профили**: пользователи могут создавать, дублировать и редактировать свои профили.  При создании нового профиля предлагается выбрать базу (встроенный), затем настроить слои, прокси, DoH, hosts и параметры автозапуска.
* **Редактирование профиля**: для каждого поля в модели предусмотрены функции валидации.  Приложение не должно позволять сохранить профиль с некорректными параметрами (например, несоответствие стратегии и выбранного слоя).

### 4.3 UX для профилей

В разделе «Профили» пользователь видит список профилей с индикаторами состояния.  Можно:

* Запустить профиль
* Остановить активный профиль
* Протестировать профиль
* Создать новый профиль
* Дублировать профиль
* Переименовать или удалить профиль
* Установить профиль по умолчанию
* Включить автоматическое включение по процессу (watcher)

Программа должна отслеживать, что профиль делает: активирует ли winws2, какую стратегию применяет, какие слои включены, какое состояние proxy и network.  При попытке удалить профиль, который в данный момент запущен, пользователь получает предупреждение.


## 5. Диагностика, логи и Bug report

Пользователь должен иметь возможность быстро понять, что происходит с программой, а разработчики — получить достаточно информации для отладки.  Диагностический слой состоит из нескольких компонентов:

### 5.1 Логирование

* **app.log** — основной лог приложения (trace/info/warn/error).  Хранится в `DedZapretData/logs/app.log`.
* **runtime.log** — лог запуска и завершения `winws2` и sing‑box.  Включает команды, PID, время работы, возращённый код, ошибки.
* **session_*.jsonl** — лог сессии пользователя; каждая команда и её результат пишутся как JSON‑объект с временной меткой.
* **audit.jsonl** — особый лог, в который пишутся события, связанные с безопасностью: создание автозапуска, изменение hosts, включение system proxy, установка DoH и т.д.
* **crash.log** — сохраняет полные трейсбеки при необработанных исключениях.
* **strategy_runs.jsonl** — тестовый лог (см. раздел 1.11).
* **singbox.log** — вывод sing‑box (если включён).

### 5.2 Диагностические проверки

Модуль diagnostics выполняет комплексную проверку:

* Состояние Windows (версия, архитектура, права администратора, кодировка путей, доступность PowerShell, WinDivert).
* Валидность конфигурационных файлов (`config.yaml`, `state.json`, `current.json`).
* Наличие `winws2.exe` и соответствующих версий WinDivert.
* Целостность runtime‑каталогов (bin, lists, utils, fake).
* Состояние реестра стратегий и наличие хотя бы одной работающей стратегии.
* Состояние активного профиля: запущен ли runtime, корректен ли PID, существуют ли файлы.
* Занятость портов, использующихся proxy и sing‑box.
* Состояние DNS, hosts и системного proxy (если управляются программой).
* Состояние задач автозапуска.

Диагностика должна выдавать понятный результат в виде таблицы или списка со статусами (OK, Warning, Error) и рекомендациями по исправлению.  Должна быть возможность получить более подробный вывод и сохранить его в файл.

### 5.3 Сбор bug report

* **Формат**: ZIP‑архив в `DedZapretData/reports/report_YYYY-MM-DD_HH-MM.zip`.
* **Содержимое**:
  * `meta.json` — сведения о версии программы, времени, OS, upstream‑версиях;
  * замаскированные `config.yaml`, `state.json`, `current.json` (удалены ключи, пароли, ссылки на proxy);
  * логи (app.log, runtime.log, session_*.jsonl и т.д., с маскировкой секретов);
  * сводка диагностики;
  * сводка реестра стратегий (без конфиденциальных аргументов);
  * `latest_strategy_ranking.json` и `problem_domains.json`;
  * список файлов в `DedZapretData` (tree.txt);
  * список установленных узлов proxy (идентификаторы без паролей).
* **Процесс**: при запуске сборщика программа создает временный каталог, копирует необходимые файлы, маскирует конфиденциальную информацию, затем упаковывает.  После успешного завершения выводит путь и объясняет, что содержимое безопасно для публикации.


## 6. Обновления, ремонт и резервное копирование

DedZapret Manager должен предоставлять пользовательские команды для обновления runtime, импортированных стратегий, ремонта повреждённого окружения и резервного копирования.

### 6.1 Обновление Flowseal runtime

* Проверяет, доступна ли новая версия (по checksum или версии), скачивает релиз в staging.
* Валидация: структура ZIP/архива соответствует ожиданиям (наличие `winws2.exe`, `WinDivert`, `bin`, `lists`, `utils`, `fake`, `general*.bat` и т.д.).
* Создаёт backup текущего runtime (`DedZapretData/backups/runtime_YYYY-MM-DD_HH-MM.zip`).
* Атомарно заменяет runtime, сохраняя права доступа.
* Перестраивает реестр стратегий и отмечает, какие стратегии требуют конверсии.
* Никогда не запускает новую стратегию без подтверждения пользователя.

### 6.2 Обновление стратегий

* Поддерживает синхронизацию Flowseal (*.bat) и StressOzz (Zapret‑Manager.sh).
* Скачивает свежие источники, извлекает стратегии, нормализует под `winws2`, классифицирует по статусам (см. **PROGRAM_BLUEPRINT.md**).
* Не удаляет пользовательские и custom‑стратегии.  В случае конфликтов предлагает варианты.
* Показывает пользователю список изменений: добавлено X, обновлено Y, конфликтов Z.

### 6.3 Ремонт runtime

* Восстанавливает отсутствующие fake‑файлы, списки и утилиты из upstream‑источников (если доступны).
* Восстанавливает WinDivert и другие зависимости.
* Создаёт недостающие каталоги и `.gitkeep` файлы, если это не влияет на работу.
* Никогда не создаёт поддельные fake‑файлы; если файл не найден в upstream, сообщает об ошибке.
* По завершении выводит отчёт, что было восстановлено и что ещё отсутствует.

### 6.4 Резервное копирование

* Позволяет создать полный backup текущего окружения: конфиги, state, current, custom стратегии, профили, runtime, логи.
* Резервная копия хранится в `DedZapretData/backups/backup_YYYY-MM-DD_HH-MM.zip`.
* Пользователь может выбрать, что включить в бэкап: только конфиги, только runtime, всё.
* При восстановлении текущие файлы сохраняются в отдельный backup.


## 7. Требования к удобству использования

DedZapret Manager должен быть дружелюбным к конечному пользователю.  Многие пользователи не будут знакомы с терминалами и DPI‑обходами, поэтому интерфейс должен быть простым и информативным.

1. **Всегда показывать состояние** — пользователь должен легко увидеть, что включено, какая стратегия работает, какие процессы запущены, изменён ли DNS, активен ли proxy, есть ли предупреждения.
2. **Ошибка = причина + решение** — сообщения должны содержать не только код ошибки, но и конкретную причину и рекомендации по исправлению.  Например: «Не найден winws2.exe. Причины: runtime не скачан, файл удалён антивирусом, путь изменён. Как исправить: обновите Flowseal runtime, выполните Repair, укажите путь вручную».
3. **Без скрытых побочных эффектов** — программа должна сообщать о предстоящих изменениях (например, модификация hosts, изменение DNS, создание задания автозапуска) и требовать подтверждения.  Для каждого действия должна быть функция «Вернуть как было».
4. **Безопасные настройки по умолчанию** — система по умолчанию не включает system proxy, не меняет DNS без явного запроса, не активирует подписки и не запускает неподтверждённые стратегии.  Запрет на автоматический fallback с `winws2` на `winws`.
5. **Возможность возврата** — перед любым потенциально опасным действием (изменением системных настроек, обновлением runtime, удалением профиля) делать резервную копию и предоставлять опцию восстановления.
6. **Режимы для новичков и продвинутых пользователей** — интерфейс должен уметь скрывать сложные детали, оставляя возможность для глубокого анализа и отображения «сырых» данных (аргументы команд, JSON‑логи) по запросу.
7. **Интернационализация** — поддержка нескольких языков, начиная с русского и английского.  Все сообщения и документация должны быть локализуемыми.  Настройку языка следует хранить в конфиге.


## 8. Заключение

Представленные здесь требования формируют основу для высокого качества обслуживания пользователей и безопасной эксплуатации DedZapret Manager.  Операционный слой должен быть не второстепенной функцией, а неотъемлемой частью проекта.  Хорошие тесты, надёжный proxy‑слой, удобный автозапуск, грамотный трей, полноценные профили, мощная диагностика, безопасные обновления и резервное копирование — всё это повышает ценность программы и делает её конкурентоспособной.  Реализация этих функций должна следовать слоистой архитектуре, описанной в **PROGRAM_BLUEPRINT.md**, и соблюдать правила безопасности, определённые в других документах.
